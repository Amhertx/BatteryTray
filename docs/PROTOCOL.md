# 协议与实现细节

三台设备的电量都走厂商 HID 协议，逐个实测得出。本文记录报文格式、判定规则和只读边界，
方便换设备时对照排查。

> 前提：这三台设备在 Windows 上都没有原生电量 API —— `Get-PnpDevice -Class Battery` 里没有它们，
> `root\wmi` 下也没有对应的 `BatteryStatus` 实例。想读数只能问厂商自己的 HID 通道。

## 支持矩阵

| 设备 | 通道 | 电量 | 充电状态 | 备注 |
|---|---|---|---|---|
| 索尼 INZONE H9 二代 | `0xFF04` / report `0x02` | ✅ | ✅ | 与 INZONE Hub 可同时使用 |
| 雷蛇 炼狱蝰蛇 V3 Pro | feature report `0x07` | ✅ | ✅ | 闲置休眠时返回「未就绪」 |
| 狼蛛 F87 Pro | 2.4G 接收器查询帧 `0x13/0x4A` | ✅ | ✅ | 无线/有线切换期间可能不应答 |

## 索尼 INZONE H9 II

`0xFF04` 通道（report id `0x02`，64 字节 Output/Input 管道），请求头固定 14 字节：

```
请求  02 0C 01 00 FC 08 96 C3 41 04 01 01 00 A0     余下补 0 至 64 字节
                                    │  └─┬─┘  └──── [13] 校验 = (cmd + 0x9C) & 0xFF
                                    │    └────────── [10] MODE：0x01=只读，0x02=写配置
                                    └─────────────── [9]  命令：0x04=电源状态，0x06=音频状态

回复  02 0E 04 FF .. 96 C3 14 04 ..
                            │  └── [13] 充电状态（1=充电中，0=未充电）
                            └───── [14] 电量百分比
```

`0x41/0x06`（音频状态）可以交叉印证：`[14]`=充电、`[15]`=电量。两条请求同时读到的值一致，
说明字段映射可靠。

INZONE Hub 可以照常开着：HID 句柄是共享打开的，本程序只发 `MODE=0x01` 的只读查询，
从不发 `MODE=0x02` 的写入，两边互不干扰（已在 Hub 运行时实测）。

## 狼蛛 F87 Pro

接收器没有纯 GET 通道，只能发查询帧收回复：

```
请求  13 4A 00 00 ... 00 5D      ← 第 20 字节 = 前 19 字节之和 & 0xFF

回复  13 4A 01 00 02 5B 10 ... CB
                    │  │  └── [6] 状态字节，两个半字节各管一件事：
                    │  │        0x01 → 低半字节 1，用电池（未插线）
                    │  │        0x10 → 高半字节 1，插线充电中
                    │  └───── [5] 电量百分比
                    └──────── [4] 回复类型
```

注意：厂商集合 `FF04/0002` 上那个 7 字节 Feature（`06 00 02 64 64 64 35 E7`）是接收器缓存的
**配置块，不是电量** —— 它的字节不会随设备状态变化。早期把这 3 个 `0x64` 读成 100% 就是踩了这个坑。

## 雷蛇 DeathAdder V3 Pro

91 字节 feature report（report id + 90 字节报文），CRC 为第 3~88 字节的异或。

| 命令 | 含义 | 字段 |
|---|---|---|
| `0x07/0x80` | 电量 | `[10]` 电平（`0x00~0xFF` 映射 `0~100%`），`[1]` 状态 |
| `0x07/0x81` | 充电状态 | `[10] == 0x01` 表示正在充电 |

`[1]` 状态字节：`0x02` 成功、`0x01` 忙（需重试）、`0x04` 设备未就绪 —— 鼠标闲置休眠时返回的就是它，
界面按「休眠」显示，并以 5 分钟间隔短重试，而不是当成读取失败。

## 只读边界

程序不修改任何设备设置，也不影响厂商软件。所有报文路径都收敛在 `btray/hidio.py` 的白名单里：

1. 读取优先走 `get_feature_report` / `read`。会写报文的只有三条**只读查询**路径 —— 雷蛇 feature 查询、
   狼蛛查询帧、索尼查询帧，这是硬件层面唯一可行的读法。
2. 白名单极窄：雷蛇只放 `0x07/0x80`、`0x07/0x81`；狼蛛只放 `0x13/0x4A`；索尼只放 `MODE=0x01` 的 `0x41/0x04`。
   其余一律拦截并记审计日志。
3. **显式封禁 `SET_DEVICE_MODE(0x00/0x04)`** —— 这条会把设备从板载模式抢到驱动模式，
   正是让雷云 DPI 切换失效的操作。
4. **显式封禁索尼的 `MODE=0x02`** —— 那是改音量 / 降噪 / 声像平衡的写入通道。
5. 查询报文载荷区必须全 0，杜绝借查询夹带配置写入；狼蛛帧强制校验长度 20、report id `0x13`、
   校验和正确；索尼帧强制校验 MODE 与校验字节。
6. HID 句柄共享打开（`FILE_SHARE_READ|WRITE`），不独占、不抢占。
7. 设备休眠 / 离线时只降级显示，不重试抢占、不重启设备。

审计日志：`%APPDATA%\BatteryTray\audit.log`，按行记录 `TX-READONLY` / `TX-QUERY` / `RX` / `BLOCKED`，
可以自行核对程序到底发过什么。

## 排错

| 现象 | 先看哪里 |
|---|---|
| 某台一直「休眠」 | `audit.log` 里 `RX` 是否返回 `0x04`；键盘按键 / 鼠标移动唤醒后应自动恢复 |
| 某台一直「离线」 | 设备是否已与接收器配对；耳机关机时只剩接收器，读不到是正常的 |
| 数值明显不对 | `python tools/watch.py scan` 打印全部 HID 设备，`watch.py query <key>` 看原始帧 |
| 程序起不来 | `%APPDATA%\BatteryTray\error.log`（`btray/diag.py` 会把异常和线程崩溃都写进去） |
